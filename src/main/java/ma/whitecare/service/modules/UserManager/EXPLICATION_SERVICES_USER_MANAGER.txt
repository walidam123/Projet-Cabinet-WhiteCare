1. VUE D'ENSEMBLE DE L'ARCHITECTURE
================================================================================

Votre application utilise une architecture en couches avec séparation claire
des responsabilités selon le principe de responsabilité unique (SRP - Single
Responsibility Principle).

HIÉRARCHIE DES ENTITÉS (Héritage Java) :
----------------------------------------
BaseEntity (classe abstraite)
    ↓
Utilisateur (classe concrète)
    ↓
Staff (classe abstraite)
    ├──→ Medecin (classe concrète)
    └──→ Secretaire (classe concrète)

HIÉRARCHIE DES SERVICES (Composition et Délégation) :
----------------------------------------------------
UserService
    ↓ (utilisé par)
StaffService
    ↓ (utilisé par)
MedecinService ────┐
                   ├──→ (utilisent UserService)
SecretaireService ─┘

5. CONCEPTS ET PATTERNS UTILISÉS
================================================================================

5.1. PRINCIPE DE RESPONSABILITÉ UNIQUE (SRP - Single Responsibility Principle)
─────────────────────────────────────────────────────────────────────────────
Chaque service a UNE SEULE responsabilité :
- UserService : Gestion des Utilisateurs
- StaffService : Gestion des Staff
- MedecinService : Gestion des Médecins
- SecretaireService : Gestion des Secrétaires

5.2. PRINCIPE DE SÉPARATION DES CONCERNS (Separation of Concerns)
─────────────────────────────────────────────────────────────────────────────
Séparation claire entre :
- Gestion des utilisateurs (UserService)
- Gestion du personnel (StaffService)
- Gestion des spécialités (MedecinService, SecretaireService)

5.3. PRINCIPE D'OUVERTURE/FERMETURE (OCP - Open/Closed Principle)
─────────────────────────────────────────────────────────────────────────────
- Ouvert à l'extension : Ajouter un nouveau type de Staff (ex: Infirmier)
  → Créer InfirmierService sans modifier les services existants
- Fermé à la modification : Les services existants restent inchangés

5.4. PRINCIPE DE SUBSTITUTION DE LISKOV (LSP - Liskov Substitution Principle)
─────────────────────────────────────────────────────────────────────────────
Medecin et Secretaire peuvent être utilisés partout où Staff est attendu

5.5. PRINCIPE D'INVERSION DES DÉPENDANCES (DIP - Dependency Inversion Principle)
─────────────────────────────────────────────────────────────────────────────
Les services dépendent d'abstractions (interfaces) :
- MedecinService dépend de UserService (interface), pas de UserServiceImpl
- SecretaireService dépend de StaffService (interface), pas de StaffServiceImpl

5.6. COMPOSITION AU LIEU D'HÉRITAGE (Composition over Inheritance)
─────────────────────────────────────────────────────────────────────────────
Les services utilisent la COMPOSITION :
- MedecinService contient une référence à UserService
- MedecinService contient une référence à StaffService
- Au lieu d'hériter de UserService ou StaffService

5.7. DÉLÉGATION (Delegation Pattern)
─────────────────────────────────────────────────────────────────────────────
Chaque service délègue les responsabilités à d'autres services :
- MedecinService délègue la gestion Utilisateur → UserService
- MedecinService délègue la gestion Staff → StaffService
- MedecinService gère uniquement les aspects spécifiques Médecins

5.8. PATTERN DTO (Data Transfer Object)
─────────────────────────────────────────────────────────────────────────────
Utilisation de DTOs pour :
- CreateMedecinDTO, UpdateMedecinDTO
- MedecinDTO, MedecinStatisticsDTO
- Séparation entre couche présentation (DTO) et couche métier (Entity)

5.9. VALIDATION CENTRALISÉE
─────────────────────────────────────────────────────────────────────────────
- UserValidator : Validation des données Utilisateur
- StaffValidator : Validation des données Staff
- MedecinValidator : Validation des données Médecin
- SecretaireValidator : Validation des données Secrétaire

5.10. GESTION D'EXCEPTIONS MÉTIER
─────────────────────────────────────────────────────────────────────────────
Exceptions personnalisées :
- UserNotFoundException
- StaffNotFoundException
- MedecinNotFoundException
- SecretaireNotFoundException
- CabinetNotFoundException
- UserAlreadyExistsException

7. FLUX DE CRÉATION D'UN MÉDECIN (EXEMPLE)
================================================================================

ÉTAPE 1 : Appel du contrôleur
──────────────────────────────
Controller → MedecinService.createMedecin(CreateMedecinDTO)

ÉTAPE 2 : MedecinService traite la requête
──────────────────────────────────────────
MedecinService.createMedecin() {
    1. Validation des données (MedecinValidator)
    2. Vérification unicité (login, CIN)
    3. Vérification cabinet existe
    
    4. DÉLÉGATION à UserService :
       → UserService.createUser(CreateUserDTO)
       → Crée l'Utilisateur en base
       → Assigne le rôle MEDECIN
       → Retourne Utilisateur créé
    
    5. Création de l'entité Medecin :
       → Medecin medecin = new Medecin()
       → medecin.setIdUser(utilisateur.getIdUser())
       → medecin.setSpecialite(...)
       → medecin.setSalaire(...)  ← Données Staff
       → medecin.setCabinetMedicaleId(...)
    
    6. Sauvegarde :
       → MedecinRepository.create(medecin)
       → Crée les enregistrements dans staff ET medecin
    
    7. Retourne Medecin créé
}

ÉTAPE 3 : UserService traite la création Utilisateur
──────────────────────────────────────────────────────
UserService.createUser() {
    1. Validation (UserValidator)
    2. Vérification unicité (login, CIN, email)
    3. Hashage du mot de passe
    4. Création Utilisateur
    5. Sauvegarde via UtilisateurRepository
    6. Assignation des rôles via RoleRepository
    7. Retourne Utilisateur
}

ÉTAPE 4 : Résultat
──────────────────
Medecin créé avec :
- Utilisateur créé (table utilisateur)
- Staff créé (table staff)
- Medecin créé (table medecin)
- Rôle MEDECIN assigné (table utilisateur_role)

DIAGRAMME DE SÉQUENCE :
───────────────────────
Controller
    │
    ├─→ MedecinService.createMedecin()
    │       │
    │       ├─→ UserService.createUser()
    │       │       │
    │       │       ├─→ UtilisateurRepository.create()
    │       │       └─→ RoleRepository.assignRole()
    │       │
    │       └─→ MedecinRepository.create()
    │               │
    │               └─→ (crée dans staff ET medecin)
    │
    └─→ Retourne Medecin

8. AVANTAGES DE CETTE ARCHITECTURE
================================================================================

✅ 1. MAINTENABILITÉ
   - Code organisé et facile à comprendre
   - Chaque service a un rôle clair
   - Modifications isolées (changer MedecinService n'affecte pas SecretaireService)

✅ 2. TESTABILITÉ
   - Chaque service peut être testé indépendamment
   - Mock facile des dépendances (UserService, StaffService)
   - Tests unitaires ciblés

✅ 3. RÉUTILISABILITÉ
   - UserService réutilisable pour tous types d'utilisateurs
   - StaffService réutilisable pour tous types de Staff
   - Logique commune centralisée

✅ 4. EXTENSIBILITÉ
   - Ajouter un nouveau type de Staff (ex: Infirmier) :
     → Créer InfirmierService
     → Utiliser UserService et StaffService existants
     → Aucune modification des services existants

✅ 5. SÉPARATION DES PRÉOCCUPATIONS
   - Gestion utilisateur ≠ Gestion staff ≠ Gestion spécialités
   - Chaque couche gère son niveau d'abstraction

✅ 6. RESPECT DES PRINCIPES SOLID
   - SRP : Chaque service une responsabilité
   - OCP : Ouvert à l'extension, fermé à la modification
   - LSP : Substitution possible (Medecin IS-A Staff IS-A Utilisateur)
   - ISP : Interfaces séparées (UserService, StaffService, etc.)
   - DIP : Dépendance d'abstractions (interfaces)

✅ 7. ÉVOLUTIVITÉ
   - Facile d'ajouter de nouvelles fonctionnalités
   - Facile de modifier un service sans impacter les autres
   - Architecture scalable

10. EXEMPLE CONCRET : CRÉATION D'UN MÉDECIN
================================================================================

CODE APPELÉ :
─────────────
MedecinService.createMedecin(CreateMedecinDTO dto) {
    
    // 1. Validation
    validateCreateMedecinData(dto);
    
    // 2. Vérification unicité
    checkUniqueness(dto);
    
    // 3. DÉLÉGATION à UserService pour créer l'Utilisateur
    CreateUserDTO userDTO = convertToCreateUserDTO(dto);
    Utilisateur user = userService.createUser(userDTO);
    // → UserService gère : création, hashage password, assignation rôle
    
    // 4. Création de l'entité Medecin
    Medecin medecin = convertToMedecin(dto);
    medecin.setIdUser(user.getIdUser());
    
    // 5. Sauvegarde via repository
    medecinRepository.create(medecin);
    // → Crée dans table staff ET medecin
    
    return medecin;
}

POURQUOI CETTE APPROCHE ?
──────────────────────────
✓ UserService gère TOUS les aspects Utilisateur (cohérence)
✓ MedecinService se concentre sur les aspects spécifiques Médecin
✓ Réutilisation de la logique UserService
✓ Séparation claire des responsabilités

12. RÉSUMÉ : POURQUOI 4 SERVICES ?
================================================================================

1. SÉPARATION PAR NIVEAU D'ABSTRACTION
   ────────────────────────────────────
   UserService    → Niveau Utilisateur (le plus générique)
   StaffService   → Niveau Staff (intermédiaire)
   MedecinService → Niveau Médecin (spécialisé)
   SecretaireService → Niveau Secrétaire (spécialisé)

2. PRINCIPE DE RESPONSABILITÉ UNIQUE (SRP)
   ────────────────────────────────────────
   Chaque service gère UN SEUL aspect du système

3. RÉUTILISABILITÉ
   ────────────────
   UserService et StaffService sont réutilisables par tous les types

4. EXTENSIBILITÉ
   ─────────────
   Ajouter un nouveau type (ex: Infirmier) :
   → Créer InfirmierService
   → Utiliser UserService et StaffService existants
   → Aucune modification des services existants

5. MAINTENABILITÉ
   ──────────────
   Code organisé, facile à comprendre et à modifier

6. TESTABILITÉ
   ───────────
   Chaque service peut être testé indépendamment

7. RESPECT DES PRINCIPES SOLID
   ────────────────────────────
   Architecture propre et professionnelle

13. CONCLUSION
================================================================================

Votre architecture suit les meilleures pratiques de développement logiciel :

✓ Séparation claire des responsabilités
✓ Réutilisation de code (DRY - Don't Repeat Yourself)
✓ Extensibilité (OCP - Open/Closed Principle)
✓ Testabilité
✓ Maintenabilité
✓ Évolutivité

Cette approche permet de :
- Développer plus rapidement (réutilisation)
- Maintenir plus facilement (code organisé)
- Tester plus efficacement (services isolés)
- Évoluer plus sereinement (extensibilité)

C'est une architecture professionnelle et scalable ! 🎯
